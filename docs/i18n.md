# Interface languages

Status: written as a plan on 2026-10-13 for issue #13, and changed after a review by Codex (gpt-6-astra) on the same day. Chris approved the Paper design on 2026-10-14. All nine phases are on `main` since 2026-10-14 (#16). On 2026-10-14 Chris decided to ship the `es`, `pt-BR`, `zh-CN`, and `ja` catalogs without a native review, because an imperfect translation is better than none. All four have `draft: false`. Corrections from native speakers are welcome as pull requests. On 2026-10-17 Chris added `de`, `fr`, `it`, `ko`, and `ru` (see "More locales").

This file says how the Sayso interface shows text in more than one language. English is the source language. The first translations are Spanish, Portuguese (Brazil), Simplified Chinese, and Japanese.

The dictation language (see `CONTEXT.md`) is a different setting. It is the language the user speaks. The interface language is the language of the text that Sayso shows.

## Decisions

Chris made these decisions on 2026-10-13.

- The infrastructure comes first. No translation starts before the infrastructure is on `main`.
- The first four locales are `es`, `pt-BR`, `zh-CN`, and `ja`.

These decisions follow issue #13 and the code:

- The library is rust-i18n 4, which gpui-component already uses. rust-i18n keeps one locale for the process, so one `set_locale` call also changes the text of the kit widgets (the select placeholder, the calendar). gpui-component has catalogs for `en`, `zh-CN`, `zh-HK`, `zh-TW`, and `it`. Its widgets show English in `es`, `pt-BR`, and `ja` until it has catalogs for them.
- The setting is `[general] language`, with the value `"system"` (the default) or a locale code. A change applies at once, without a restart.
- Keys are names, not English sentences: `overlay.notice.download_model`, not `"Download a speech model first"`. A change to the English text then does not lose the translations, and two places with the same English text can get different translations.
- Each locale has one folder of catalog files, one file for each surface: `crates/sayso-i18n/locales/<locale>/<surface>.<locale>.yml`. Several agents and translators can then work at the same time without conflicts. To add a locale, add its folder and one line in `LOCALES`.
- A key is always a string literal in the `t!` call, so a test can check it. A text with a version for each system has one key for each version, with a suffix: `launch_detail_mac`, `launch_detail_windows`, `launch_detail_other`. `os_text!` selects the key: `t!(os_text!("a_mac", "a_other"))`. The suffix is not a nested key, because `.other` is also a plural category.

## Terms

These terms go into `CONTEXT.md` with the code.

**Interface language**
The language of the text that Sayso shows. The setting `general.language` selects it. The value `"system"` takes the first language of the system that Sayso has a catalog for, else English.

**Catalog**
The file with the text of one locale, keyed by name.

**Locale**
A code such as `en`, `pt-BR`, or `zh-CN` that names one catalog.

## The `sayso-i18n` crate

A new crate with no Sayso and no GPUI dependencies. `sayso-core` may depend on it, so that config messages can be translated. All other crates may depend on it.

It contains:

- The catalogs, compiled into the binary with `rust_i18n::i18n!`.
- `LOCALES`: every locale with a catalog folder, each with its native name ("Español", "日本語") and a `draft` flag. A first translation is a draft until a native speaker reviews it. `available()` gives the locales that the Language menu offers and that "system" can select: all of them in a debug build, only the reviewed ones in a release. A test checks that the folders and `LOCALES` match, and that each catalog, also a draft, has every key of English.
- `t!`: the lookup macro. rust-i18n's own `t!` expands to items of the crate that calls it, so it works only in the crate that has the catalogs. `sayso_i18n::t!` calls functions of `sayso-i18n` instead, so every crate can use it.
  - `t!("key")` gives the text.
  - `t!("key", name = value)` puts `value` in the place of `%{name}`.
  - `t!("key", count = n)` selects `key.one`, `key.many`, or `key.other` with the plural rule of the locale, and puts `n` in the place of `%{count}`. `count` must be the first argument. Counts are whole numbers (`u64`). A text with a decimal number does not use a plural.
- `set_locale(code)` and `locale()`. `set_locale` calls `rust_i18n::set_locale`, so the kit widgets change too.
- `resolve(setting, system_locales)`: the locale to use. Rules, in order:
  1. A setting other than `"system"` that is in `LOCALES` wins.
  2. Else, each system locale in order: an exact match, then a match on the language only (`pt-PT` gives `pt-BR`, `es-MX` gives `es`, `zh-Hans-CN` gives `zh-CN`). Traditional Chinese (`zh-Hant`, `zh-TW`, `zh-HK`, `zh-MO`) does not match `zh-CN`.
  3. Else `en`.
- Plural rules for the locales in `LOCALES`, from CLDR, for whole numbers: `en` and `de` have `one` for 1. `es` and `it` have `one` for 1 and `many` for a whole number of millions. `pt-BR` and `fr` have `one` for 0 and 1, and `many` like `es`. `ru` has `one` (1, 21, 31, but not 11), `few` (2-4, 22-24, but not 12-14), and `many` for the rest; its `other` is for fractions, which counts never are. `zh-CN`, `ja`, and `ko` have only `other`. A category that a catalog does not have falls back to `other`, but the parity test requires each category that the counts of the language give.
- `numbers::integer` and `numbers::decimal` write numbers with the separators of the locale, from CLDR: "1,234.5" in English, "1.234,5" in German, "1 234,5" in French and Russian (a no-break space; the bundled fonts have no narrow no-break space, so French text uses U+00A0 also before "?", "!", ":", and ";"). A number in an input or in `config.toml` keeps the decimal point.
- A pseudo-locale for development, `en-XA`. It is not in `LOCALES`. It changes each English text to accented letters in brackets, about 30% longer: "Save" shows as "[Šåvé~~]". Placeholders stay as they are. Text that shows without brackets is not in a catalog yet. Only a debug build has it: there the flag `--pseudo`, `language = "en-XA"`, or the Language menu turns it on. A release treats `en-XA` as an unknown setting, reports it as a config problem, and follows the system.

The system locales come from the `sys-locale` crate, which is already in the dependency tree.

A missing key shows the English text. If the English text is also missing, the key shows. A test makes sure that this does not happen in a release (see "Tests").

`resolve` accepts the pseudo-locale as a setting, although it is not in `LOCALES`. A setting matches a locale without regard to case. In a Chinese tag, an explicit script wins over the region: `zh-Hant-CN` is Traditional.

## The app

- At startup, before the first window opens, the app resolves the locale and calls `set_locale`.
- `apply_config_change` does the same when `general.language` changes, and emits `AppEvent::LanguageChanged`. On that event the app redraws all windows and builds the tray menu again.
- Views that keep text in state get it again on `LanguageChanged`, or keep the key and the arguments instead of the text. The review found these: input placeholders (Settings › General, and the search field of gpui-component lists), the tray menu (the Linux tray can change only its image now, so it needs a call to change its labels), window titles (also the What's New window), errors in Dictionary, notices in History, and the extra labels of the model picker. Each phase handles the stored text of its surface. Settings › General does it in phase 1.
- Settings › General gets a **Language** group as its first group. The Paper design is on the page "Languages" in "Sayso — v0.1 Design". The select shows "**System** English" (the setting, then the language that it gives, in graphite) or the name of the chosen language. The menu has "System" first, a rule, then each entry of `LOCALES`. Each line shows the name of the language in that language ("Español"), and on the right its name in the interface language ("Spanish", from `language_name` and the `language.*` keys). Each name is in its own language, so a user who cannot read the current language can still find their own.

## Fonts

The bundled fonts (Fraunces, Instrument Sans, IBM Plex Mono) have no Chinese or Japanese characters. Chinese and Japanese share many characters with different shapes, so the system must not choose the fallback font: on a system in English, macOS would show Japanese text with a Chinese font. `sayso_ui::fonts::fallbacks` gives a fallback list for each locale and face:

| Locale | Sans (Instrument Sans) | Serif (Fraunces) |
|---|---|---|
| `ja` | Hiragino Sans, Yu Gothic UI, Noto Sans CJK JP | Hiragino Mincho ProN, Yu Mincho, Noto Serif CJK JP |
| `zh-CN` | PingFang SC, Microsoft YaHei UI, Noto Sans CJK SC | Songti SC, SimSun, Noto Serif CJK SC |
| `ko` | Apple SD Gothic Neo, Malgun Gothic, Noto Sans CJK KR | AppleMyungjo, Batang, Noto Serif CJK KR |
| `ru` | The system's choice | Georgia, Noto Serif |
| Others | The system's choice | The system's choice |

The bundled fonts have no Cyrillic. Without a list, the system shows Russian serif text in a sans face.

Each window root sets the sans list of the interface language with `.locale_fonts(Face::Sans)`, and the children inherit it. Each text in Fraunces sets the serif list. A menu sets the sans list again, because it draws in a deferred layer. A line of the Language menu uses the fonts of its own locale (`fonts_for`), so "日本語" has a Japanese font also when the interface is in Chinese. GPUI uses the list on macOS and Windows. On Linux, GPUI ignores it and fontconfig selects the font.
- `Config::validate` reports a `general.language` value that is not `"system"`, not in `LOCALES`, and not `en-XA`. The app then uses `"system"`.

## How to move text into a catalog

These rules are for each migration phase.

1. Put the English text in a catalog file of the surface: `crates/sayso-i18n/locales/en/<surface>.en.yml` (see `locales/README.md`). Use the key prefix of the surface: `overlay.`, `popover.`, `tray.`, `update.`, `whats_new.`, `onboarding.`, `home.`, `history.`, `dictionary.`, `styles.`, `models.`, `model_picker.`, `hub.`, `settings.<page>.`. Keys are `snake_case` names of what the text is for, not the text.
2. In the code, use `sayso_i18n::t!` with a literal key. Arguments go in as `t!("key", name = value)`, never by `format!` around a translated piece. A whole sentence is one key. Do not join translated pieces into a sentence, because the word order differs between languages.
3. Plurals: `t!("key", count = n)` with `count` first, and `one` and `other` under the key in the catalog.
4. Text for each system: one key for each version with the suffix `_mac`, `_windows`, `_other`, and `t!(crate::shell::os_text!("key_mac", "key_other"))`.
5. Dates: `sayso_i18n::dates`. Never format a date with an English chrono pattern such as `%B %-d`. Clock times (`%-H:%M`) can stay.
6. Text that a view keeps in a field (an input placeholder, a stored message) must change with the language. Keep the key and the arguments, or set the text again when `sayso_i18n::locale()` changes (Settings › General does this for its placeholder).
7. Do not translate: model, provider, and vendor names, "Sayso", key names (Option, Ctrl, Esc), file names and paths, `config.toml` keys and values, log messages, developer-only text (`dev.rs`), and text from the user. Error text from a provider or the system stays as it is; put it in an argument of a translated sentence.
8. Check with `cargo test -p sayso-i18n` (missing keys, unused keys, literal keys) and `cargo clippy --workspace --all-targets -- -D warnings`, then run the app with `--pseudo` and look for text without brackets.

## Two blockers

These change before any text moves into a catalog.

1. **The overlay selects its icon from English words.** `overlay/mod.rs` shows a mic icon when the notice contains "microphone", and a lock when it contains "password". With translated text, the icons go wrong. The fix: `blocked_notice` becomes a `Notice` with an `icon` field that the producer sets, and the incognito detail moves into the notice as a field.
2. **The `os_text!` constants hold English text.** `os_text!` itself can stay: it selects any expression, so it can select a key. The constants in `shell/mod.rs` (`COMPUTER`, `SECRET_STORE`, ...) are `&'static str` with English text. They become functions that return translated text: `t!(os_text!("os.computer_mac", "os.computer_pc", "os.computer_other"))`. Each site changes with its surface. The constants move in phase 2.

## What is not translated

- Model names, provider names, and vendor names.
- Text from the user: styles, dictionary words and replacements, history.
- Log messages and the keys and values in `config.toml`.
- Release notes, the README, and the website, for now.
- Error text that comes from a provider or a system API. Sayso shows its own translated sentence and puts the original text after it.
- The text of the kit widgets in a locale that gpui-component has no catalog for. In the pseudo-locale, this text shows without brackets. That is not an error.

## Phases

Each phase is one pull request. After each phase, `main` builds, the tests pass, and the app is complete in English.

1. **Foundation.** The crate, `t!`, plurals, the pseudo-locale, `resolve`, the setting, the Language group (it shows when `LOCALES` has more than English, or in a debug build), the live change, the fallback fonts, the `Notice` fix, the dependency rule, the catalog tests. The overlay notices and Settings › General move into the catalog as the first users.
2. **Overlay, popover, tray, and the `os_text!` constants.**
3. **Onboarding.**
4. **Hub pages**: Home, History, Dictionary, Styles, Models.
5. **Settings pages** and the model picker.
6. **Text from other crates**: config messages in `sayso-core`, errors from `sayso-enhance` and `sayso-update`, the permission and system text in the platform crates. Dates and times in History use the locale.
7. **Text from the engines.** The Swift engine sends English sentences, for example why Apple Intelligence is not available (`LanguageModel.swift`) and that a download is not complete (`Engine.swift`). The client keeps them (`sayso-engine-client/src/protocol.rs`) and Models shows them. The engines send a stable error code and its arguments in addition to the text, and the app translates the code. The original text stays as detail.
8. **System files**: the catalog `system` holds the text that the system shows outside the app. `scripts/i18n-system-files.py` writes `packaging/macos/<lproj>/InfoPlist.strings` (the microphone prompt; `bundle.sh` copies the folders into the app), the `GenericName[xx]`, `Comment[xx]`, `Keywords[xx]`, and action `Name[xx]` lines of the Linux desktop entry, and the `xml:lang` lines of the metainfo file. It writes only reviewed locales. CI runs it with `--check`. The Windows installer uses the official Inno Setup files for Spanish, Brazilian Portuguese, and Japanese. Simplified Chinese gets the English installer until Inno Setup has an official file.
9. **Translations**: one pull request for each locale. A model writes the first draft from the English catalog and a glossary built from `CONTEXT.md`. A native speaker reviews each locale before it goes into `LOCALES`. The author of issue #13 offered to do `zh-CN`.

## Tests

- **Parity.** For each locale in `LOCALES`: the catalog has every key of `en.yml`, has no key that `en.yml` does not have, and each text has the same `%{...}` placeholders as the English text. Plurals compare by their base key, because the categories differ between languages, and each plural has `other`.
- **No missing keys.** A test collects the key literals from all `t!` calls in the workspace, also the keys in `t!(os_text!(...))`, and checks that `en.yml` has each one. A plural call needs `key.other`. The test fails for a `t!` call whose key is not a literal. This catches a typo in a key, which would otherwise show the key in the UI.
- **No unused keys.** Each key in `en.yml` occurs as a literal in the code, so that translators do not translate dead text.
- **Resolve.** Unit tests for the rules above, also `zh-Hant`, `zh-Hant-CN`, `pt-PT`, POSIX tags such as `zh_CN.UTF-8`, an unknown setting, and an empty system list.
- **Plurals.** Unit tests for each rule.
- **Visual check.** After each migration phase, run the app with the pseudo-locale and look for text without brackets. Long German-like text is not a target, but the pseudo-locale makes each text about 30% longer, so it also shows text that does not fit.

## Open questions

- Key names that Sayso writes itself ("Right ⌥") and the reasons why a hotkey cannot register stay in English.
- Onboarding saves a new custom endpoint with the English name "Custom endpoint". It is a name in the config, so it does not change with the language.
- A `generate` error of the language model carries a `reason`, but `sayso-enhance` does not read it yet. The provider test in Settings › Providers still matches English words in the error.
- The names of system shortcuts in the hotkey conflict notes are translations, not checked against the menus of each system.
- Should `pt` be `pt-BR` only, or should a later `pt-PT` catalog override it? The plan uses `pt-BR` and maps `pt-PT` to it until someone asks for `pt-PT`.
- Traditional Chinese users get English, not Simplified Chinese. gpui-component has `zh-TW` and `zh-HK`, so a later `zh-TW` catalog is cheap.

## More locales

On 2026-10-17 Chris added `de`, `fr`, `it`, `ko`, and `ru`. A model wrote each catalog from the English catalog and the glossary, as in phase 9. On the same day Chris decided to ship them as final (`draft: false`) without a native review, as with the first four. gpui-component has a catalog for `it` only of the five, so its widgets show English in the other four.
